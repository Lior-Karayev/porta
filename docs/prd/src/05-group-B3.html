9User Stories and Use Scenarios

Each story names the requirements it implements and belongs to one feature group (P-Fxx). Retired stories and criteria are listed in Section 7.6. Acceptance criteria use the form Given (state before) · When (what happens) · Then (verifiable result). The type column marks each criterion as H (happy path: everything works as expected), E (error state: what the user sees and can do when something fails) or X (edge case: empty input, missing data, duplicate action, concurrency).

US-01 · As a resident, I want to create a one-time permission for my guests, so that they can enter on the evening of the visit without me opening the gate. P-F02 · Implements FR-06, FR-08, FR-15
AC-01.1HGiven an approved resident and an active gate "Main", when they create a one-time permission for "Noa" on Fri 19:00–23:59 at "Main" with limit 2, then it is saved and displayed as SCHEDULED (or ACTIVE if the start has already passed), its link is generated, and it appears in the list (S-02) with "2 of 2 openings left".
AC-01.2EGiven the creation form, when the end time is before or equal to the start, or more than 7 days after it, then the form shows an inline error on the end field, the Save button stays disabled, and nothing is saved.
AC-01.3XGiven the creation form, when the guest name is empty or only spaces, or no gate is selected, then an inline "required" message is shown and nothing is saved.
AC-01.4EGiven no internet connection, when the resident taps Save, then the app shows "No connection. Your permission was not saved.", keeps everything entered, and offers Retry. No link exists until the save succeeds.
AC-01.5XGiven a slow connection, when the resident taps Save twice quickly, then exactly one permission is created (the button is disabled while the save is in progress, and a repeated save with the same request ID returns the first result without creating another permission or link, FR-16).
US-02 · As a resident, I want to give my cleaner recurring access on Tuesdays 08:00–12:00, so that I don't have to be home to let them in. P-F02 · Implements FR-07, FR-08, FR-13
AC-02.1HGiven a recurring permission for Tuesdays 08:00–12:00 from 1 Dec 2026 to 31 Mar 2027 with limit 40, when the guest requests an opening on Tue 1 Dec 2026 at 09:15 (community time zone), then it is granted and the used count becomes 1.
AC-02.2EGiven the same permission, when the guest requests an opening on a Wednesday, or on a Tuesday at 12:01, then it is denied with OUTSIDE_HOURS, the page shows "Your access is on Tuesdays 08:00–12:00. Next: Tue 8 Dec 08:00", and the used count does not change.
AC-02.3XGiven the creation form, when the resident sets a window that crosses midnight (e.g. 22:00–02:00) or selects no weekday, then the form explains that the window must start and end on the same day (current limitation, Q-08) or that a weekday is required, and nothing is saved.
AC-02.4XGiven a window 08:00–12:00, when a request is made at exactly 08:00:00 or exactly 12:00:00, then 08:00:00 is granted and 12:00:00 is denied (the window is start-inclusive and end-exclusive).
US-03 · As a resident, I want to suspend a permission and resume it later, so that I can block access temporarily without recreating anything. P-F02 · Implements FR-10, FR-13
AC-03.1HGiven an ACTIVE permission with 3 of 5 openings used, when the resident suspends it, then any request is denied with SUSPENDED. After the resident resumes it, a request inside the window is granted and the count becomes 4 of 5. The count was not reset.
AC-03.2EGiven the resident suspends a permission while the device is offline, when the action fails, then the status shown does not change, "Not suspended: no connection" is displayed, and Retry is offered.
US-04 · As a resident, I want to cancel a permission permanently, so that a guest I no longer trust can't get in. P-F02 · Implements FR-11, FR-21
AC-04.1HGiven an active permission, when the resident confirms Cancel, then the status becomes CANCELLED within 2 s. Its link page shows "This invitation was cancelled by your host", and any open request is denied with CANCELLED.
AC-04.2XGiven a cancelled permission, when the resident looks at it, then the Suspend and Resume actions are not available. A repeated cancel request (e.g. from a second device) changes nothing and returns success.
AC-04.3XGiven the resident taps Cancel, when the confirmation dialog appears and they tap "Keep", then nothing changes.
US-05 · As a resident, I want to share the invitation link or show a QR code, so that my guest receives access the way that is easiest for them. P-F03 · Implements FR-15, FR-16, FR-18
AC-05.1HGiven a saved permission, when the resident taps Share, then the device share sheet opens with a message containing the guest-facing summary and the link. Choosing "Copy link" puts the exact link on the clipboard and shows a "Copied" confirmation.
AC-05.2HGiven a saved permission, when the resident taps "Show QR", then a QR code is displayed, and scanning it with a phone camera opens the same invitation page (W-01).
AC-05.4XGiven a link that was shared with the wrong person, when the resident cancels the permission (US-04) and creates a new one, then the old link shows the cancelled state, and the new permission has its own new link (link regeneration is out of scope, Section 7.6).
US-06 · As a resident, I want to see who entered with my permissions and be notified when they do, so that I know my guests arrived. P-F05 · Implements FR-26, FR-27, FR-29
AC-06.1HGiven a granted opening for guest "Noa" at gate "Main", when the resident opens Activity (S-06), then the event appears at the top with time, guest, gate and result "Granted".
AC-06.2aHShould Given notifications are allowed on a test Android device, when a guest is granted an opening, then a push notification "Noa entered via Main" arrives within 10 s in at least 19 of 20 trials. The delivery service itself gives no guarantee.
AC-06.2EGiven the resident refused the notification permission, when a guest enters, then no push notification is sent, the event still appears in Activity, and the home screen shows a dismissible tip about enabling notifications.
AC-06.3XGiven a resident with no events yet, when they open Activity, then an empty state explains "No entries yet. Activity appears here after your guests use their invitations."

9.2 Guest stories

IDTypeAcceptance criterion
US-07 · As a guest, I want to open the gate from the link I received, without installing anything, so that I can get in quickly. P-F04 · Implements FR-19, FR-20, FR-24, FR-26
AC-07.1HGiven a valid, active permission with 2 openings left, when the guest opens the link in a mobile browser and taps "Open gate · Main", then within 2 s (NFR-01) the page shows "Gate opening", the simulator (S-10) shows Main as OPEN for 5 s, the page shows "1 opening left", and a Granted event is logged.
AC-07.2EGiven the guest's connection drops after tapping, when no server response arrives within 10 s, then the page shows "We couldn't confirm the gate opened. Check the gate and tap to try again." The counter changes only if the server granted the request. Retrying with the same request ID returns the original result, including the remaining count, and never counts twice, even if the first response was lost after the server committed.
AC-07.3XGiven a page showing "Open gate", when the guest taps the button several times within 3 s, then exactly one request is processed and at most one opening is counted. The button shows "Opening…" and stays disabled while the request is in flight. After a grant it stays disabled until the 5-second opening ends, with a visible countdown.
AC-07.4XGiven a permission for gate Main, when the page loads, then exactly one "Open gate · Main" button is shown. If Main is inactive, the button is disabled and shows "Temporarily unavailable" (AC-11.3). A request crafted for any other gate is denied with GATE_NOT_ALLOWED, and nothing is counted.
US-08 · As a guest, I want a clear explanation when I can't get in, so that I know what to do next. P-F04 · Implements FR-13, FR-21, FR-08
AC-08.1EGiven a permission whose start is in the future, when the guest opens the link, then the page shows "Your access starts on [date, time]", the Open button is disabled, and a "Check again" action reloads the status. The page also refreshes itself when the window opens, if it is still open in the browser.
AC-08.2EGiven a permission with used = limit, when the guest opens the link, then the page shows "No openings left. Contact your host." and requests are denied with EXHAUSTED.
AC-08.3EGiven a mistyped or made-up link, when it is opened, then a generic page "This invitation link isn't valid" is shown. It contains no gate, community or person details, and the attempt is counted toward rate limiting (NFR-06).
AC-08.4XGiven a permission with exactly 1 opening left, when two devices request an opening at the same moment, then exactly one is granted, the other is denied with EXHAUSTED, and the final used count equals the limit.
US-09 (Could) · As a registered guest with the app installed, I want the invitation link to open in the app, so that I have a native experience. P-F03 · Implements FR-22
AC-09.1HGiven the app is installed on a supported device, when the invitation link is tapped, then the app opens the invitation screen (S-11) for that invitation, with the same information and actions as W-01.
AC-09.2XGiven the app is not installed or link verification is unavailable, when the link is tapped, then the browser page W-01 opens and works fully.

What it shows: the server-side handling of every opening request. The table lists the checks in order, each with its denial reason. Why it matters:
  • All reads and writes happen inside one atomic transaction: the receipt, invitation, permission and gate checks, and then the counter, gate open-until time, event and receipt writes. A concurrent cancel, suspend, or change to the owner's membership or the gate's active flag therefore can't slip in between a check and the grant, and concurrent requests can never exceed the limit (AC-08.4).
  • The invitation is validated first. The per-IP limit applies only to invalid links, so valid retries are never blocked by it. Receipts are then looked up before the per-invitation quota, so a retry of a request that was already committed always gets its stored result (AC-07.2) and is never refused as rate-limited. A request ID reused for a different gate is rejected without counting.
  • If the outcome of the commit is unknown to the client (for example the connection drops), the page treats it as unconfirmed and offers a retry with the same request ID. The server logs the failure whenever storage is available.
  • Invalid links reveal nothing.
  • A transaction that fails because of a concurrent write is retried by the server up to 3 times, re-running every check on fresh data. Two simultaneous requests for the last opening therefore end as one grant and one EXHAUSTED (AC-08.4). Any other error, or a conflict after the retries, results in a denial. The system fails closed (NFR-11).
  • Receipts: every request that reaches the receipt lookup gets its own receipt (E-08), keyed by invitation and request ID and storing the requested gate. DUPLICATE_REQUEST is answered from the existing receipt and adds none. RATE_LIMITED denials create no receipt; they are counted in one summary record per minute (FR-26), and a retry after the limit is processed normally.
  • Push notifications are sent only after the commit.
All time checks use the community's time zone (FR-06, FR-07).
