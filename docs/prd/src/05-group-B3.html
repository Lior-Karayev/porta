9User Stories and Use Scenarios

Each story names the requirements it implements. Acceptance criteria use the form Given (state before) · When (what happens) · Then (verifiable result). The type column marks each criterion as H (happy path: everything works as expected), E (error state: what the user sees and can do when something fails) or X (edge case: empty input, missing data, duplicate action, concurrency).

9.1 Resident stories

IDTypeAcceptance criterion
US-01 · As a resident, I want to create a one-time permission for my guests, so that they can enter on the evening of the visit without me opening the gate. Implements FR-06, FR-08, FR-15
AC-01.1HGiven an approved resident and an active gate "Main", when they create a one-time permission for "Noa" on Fri 19:00–23:59 at "Main" with limit 2, then it is saved with status SCHEDULED (or ACTIVE if the start has already passed), its link is generated, and it appears in the list (S-02) with "2 of 2 openings left".
AC-01.2EGiven the creation form, when the end time is before or equal to the start, or more than 7 days after it, then the form shows an inline error on the end field, the Save button stays disabled, and nothing is saved.
AC-01.3XGiven the creation form, when the guest name is empty or only spaces, or no gate is selected, then an inline "required" message is shown and nothing is saved.
AC-01.4EGiven no internet connection, when the resident taps Save, then the app shows "No connection. Your permission was not saved.", keeps everything entered, and offers Retry. No link exists until the save succeeds.
AC-01.5XGiven a slow connection, when the resident taps Save twice quickly, then exactly one permission is created (the button is disabled while the save is in progress, and the server rejects a duplicate request ID).
US-02 · As a resident, I want to give my cleaner recurring access on Tuesdays 08:00–12:00, so that I don't have to be home to let them in. Implements FR-07, FR-08, FR-13
AC-02.1HGiven a recurring permission for Tuesdays 08:00–12:00 from 1 Dec 2026 to 31 Mar 2027 with limit 40, when the guest requests an opening on Tue 1 Dec 2026 at 09:15 (community time zone), then it is granted and the used count becomes 1.
AC-02.2EGiven the same permission, when the guest requests an opening on a Wednesday, or on a Tuesday at 12:01, then it is denied with OUTSIDE_HOURS, the page shows "Your access is on Tuesdays 08:00–12:00. Next: Tue 8 Dec 08:00", and the used count does not change.
AC-02.3XGiven the creation form, when the resident sets a window that crosses midnight (e.g. 22:00–02:00) or selects no weekday, then the form explains that the window must start and end on the same day (MVP limitation, Q-08) or that a weekday is required, and nothing is saved.
AC-02.4XGiven a window 08:00–12:00, when a request is made at exactly 08:00:00 or exactly 12:00:00, then 08:00:00 is granted and 12:00:00 is denied (the window is start-inclusive and end-exclusive).
US-03 · As a resident, I want to suspend a permission and resume it later, so that I can block access temporarily without recreating anything. Implements FR-10, FR-13
AC-03.1HGiven an ACTIVE permission with 3 of 5 openings used, when the resident suspends it, then any request is denied with SUSPENDED. After the resident resumes it, a request inside the window is granted and the count becomes 4 of 5. The count was not reset.
AC-03.2EGiven the resident suspends a permission while the device is offline, when the action fails, then the status shown does not change, "Not suspended: no connection" is displayed, and Retry is offered.
US-04 · As a resident, I want to cancel a permission permanently, so that a guest I no longer trust can't get in. Implements FR-11, FR-21
AC-04.1HGiven an active permission, when the resident confirms Cancel, then the status becomes CANCELLED within 2 s. Its link page shows "This invitation was cancelled by your host", and any open request is denied with CANCELLED.
AC-04.2XGiven a cancelled permission, when the resident looks at it, then the Suspend, Resume, Edit and Regenerate actions are not available. A repeated cancel request (e.g. from a second device) changes nothing and returns success.
AC-04.3XGiven the resident taps Cancel, when the confirmation dialog appears and they tap "Keep", then nothing changes.
US-05 · As a resident, I want to share the invitation link or show a QR code, so that my guest receives access the way that is easiest for them. Implements FR-15, FR-16, FR-17, FR-18
AC-05.1HGiven a saved permission, when the resident taps Share, then the device share sheet opens with a message containing the guest-facing summary and the link. Choosing "Copy link" puts the exact link on the clipboard and shows a "Copied" confirmation.
AC-05.2HGiven a saved permission, when the resident taps "Show QR", then a QR code is displayed, and scanning it with a phone camera opens the same invitation page (W-01).
AC-05.3XGiven a link that was shared with the wrong person, when the resident taps "Regenerate link" and confirms, then the old link immediately shows the invalid-link page (W-02, INVALID_LINK), the new link works, and the used count is kept.
US-06 · As a resident, I want to see who entered with my permissions and be notified when they do, so that I know my guests arrived. Implements FR-26, FR-27, FR-29, FR-31
AC-06.1HGiven a granted opening for guest "Noa" at gate "Main", when the resident opens Activity (S-06), then the event appears at the top with time, guest, gate and result "Granted". If notifications are allowed, a push notification "Noa entered via Main" arrives within 10 s (95% of the time; the delivery service gives no guarantee).
AC-06.2EGiven the resident refused the notification permission, when a guest enters, then no push notification is sent, the event still appears in Activity, and the home screen shows a dismissible tip about enabling notifications.
AC-06.3XGiven a resident with no events yet, when they open Activity, then an empty state explains "No entries yet. Activity appears here after your guests use their invitations."

9.2 Guest stories

IDTypeAcceptance criterion
US-07 · As a guest, I want to open the gate from the link I received, without installing anything, so that I can get in quickly. Implements FR-19, FR-20, FR-24, FR-26
AC-07.1HGiven a valid, active permission with 2 openings left, when the guest opens the link in a mobile browser and taps "Open gate · Main", then within 2 s (NFR-01) the page shows "Gate opening", the simulator (S-10) shows Main as OPEN for 5 s, the page shows "1 opening left", and a Granted event is logged.
AC-07.2EGiven the guest's connection drops after tapping, when no server response arrives within 10 s, then the page shows "We couldn't confirm the gate opened. Check the gate and tap to try again." The counter changes only if the server granted the request. Retrying with the same request ID never counts twice.
AC-07.3XGiven a page showing "Open gate", when the guest taps the button several times within 3 s, then exactly one request is processed and at most one opening is counted.
AC-07.4XGiven a permission for gates Main and North, when the page loads, then one button is shown per allowed and active gate. A gate that is not allowed for this permission is never shown. A request crafted for it is denied with GATE_NOT_ALLOWED.
US-08 · As a guest, I want a clear explanation when I can't get in, so that I know what to do next. Implements FR-13, FR-21, FR-08
AC-08.1EGiven a permission whose start is in the future, when the guest opens the link, then the page shows "Your access starts on [date, time]" and the Open button is disabled.
AC-08.2EGiven a permission with used = limit, when the guest opens the link, then the page shows "No openings left. Contact your host." and requests are denied with EXHAUSTED.
AC-08.3EGiven a mistyped, made-up or regenerated link, when it is opened, then a generic page "This invitation link isn't valid" is shown. It contains no gate, community or person details, and the attempt is counted toward rate limiting (NFR-06).
AC-08.4XGiven a permission with exactly 1 opening left, when two devices request an opening at the same moment, then exactly one is granted, the other is denied with EXHAUSTED, and the final used count equals the limit.
US-09 · As a registered guest with the app installed, I want the invitation link to open in the app, so that I have a native experience. Implements FR-22, FR-23
AC-09.1HGiven the app is installed on a supported device, when the invitation link is tapped, then the app opens the invitation screen (S-11) for that invitation, with the same information and actions as W-01.
AC-09.2XGiven the app is not installed or link verification is unavailable, when the link is tapped, then the browser page W-01 opens and works fully.

9.3 Administrator stories

IDTypeAcceptance criterion
US-10 · As an administrator, I want to approve residents who join with our community code, so that only real residents can grant access. Implements FR-02, FR-03, FR-05
AC-10.1HGiven a user who joined with a valid code, when the administrator approves them, then the user's next app launch shows the resident home screen (S-02).
AC-10.2EGiven a pending user, when they try to create a permission (including by calling the server directly), then the request is rejected with "not authorized" and nothing is created.
AC-10.3XGiven a user who enters an unknown community code, when they submit, then "Community code not found" is shown and they remain unassigned.
AC-10.4HGiven an approved resident with 2 active permissions, when the administrator removes the resident, then both permissions are denied with SUSPENDED on the next request.
US-11 · As an administrator, I want to manage the community's gates and watch them in a simulator, so that the demo reflects real gate behaviour. Implements FR-04, FR-24, FR-25, FR-28
AC-11.1HGiven the administrator creates gate "North", when a resident next creates a permission, then "North" is available to select.
AC-11.2XGiven the administrator enters a gate name that already exists, or one shorter than 2 characters, when they save, then an inline error is shown and nothing is created.
AC-11.3EGiven gate "North" is deactivated, when a guest with a North-only permission opens the link, then the North button is shown as unavailable and any request is denied with GATE_INACTIVE.
AC-11.4HGiven the simulator (S-10) is open, when a grant occurs, then that gate's tile changes to OPEN within 2 s and back to CLOSED after 5 s, without a manual refresh.

9.4 Creation-helper stories

IDTypeAcceptance criterion
US-12 · As a resident unfamiliar with apps, I want a step-by-step guide to create a permission, so that I don't miss a setting. Implements FR-32
AC-12.1HGiven the wizard, when the resident completes all steps, then the review step shows a plain-language summary, and confirming creates a permission identical to one created with the form.
AC-12.2XGiven the wizard, when the resident goes Back, then previously entered answers are kept. Leaving the wizard asks for confirmation before discarding.
US-13 (Could) · As a resident, I want to type "Gardener every Sunday 7–10 until end of March", so that the permission is drafted for me. Implements FR-35
AC-13.1HGiven the text above, when the resident submits it, then a draft opens with type Recurring, Sundays, 07:00–10:00, from today until 31 Mar, with the gate and limit highlighted as "please choose". Nothing is created until the resident confirms.
AC-13.2EGiven the AI service is unavailable or takes more than 8 s, when the resident submits, then "Couldn't understand automatically. Please fill in the form." is shown, the manual form opens, and the original text stays visible.
AC-13.3XGiven ambiguous or out-of-range text (e.g. "forever", "1000 times"), when it is processed, then the draft never contains values outside FR-06/FR-07 limits. Those fields are flagged for the resident to fix.

What it shows: the order of server-side checks for every opening request, with one denial reason per branch. Why it matters: the order is deliberate.
  • Rate limiting and token checks come first, so invalid links reveal nothing.
  • Cheap status checks precede time checks.
  • The counter is checked and incremented in a single atomic transaction, so concurrent requests can never exceed the limit (AC-08.4).
  • Any error inside the transaction results in a denial. The system fails closed (NFR-11).
All time checks use the community's time zone (FR-07). The request ID makes retries idempotent (AC-07.2, AC-07.3).
