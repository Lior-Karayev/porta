8Functional Requirements

Each requirement has an ID, a description, the relevant user type, a priority and its source capability (F-xx). Requirements FR-36–FR-40 belong to post-MVP capabilities. They are listed so that every one of the 21 capabilities is traced, and they carry the priority Won't for this release.

8.1 Accounts, roles and community

FR-01A person can create an account with full name, email and password, and sign in and out. A signed-in session persists across app restarts until the user signs out or the session expires (NFR-08).Resident, AdminMustF-07
FR-02A newly registered user joins a community by entering its community code. The membership stays Pending until an administrator approves it. Pending users can only see a waiting screen.Resident, AdminMustF-07
FR-03The system enforces the role table in Section 4 on every server-side operation, not only in the user interface. A disallowed operation is rejected and makes no change.AllMustF-07

FR-05An administrator can approve or reject pending residents, and remove an approved resident. Removing a resident suspends all of that resident's permissions immediately (status SUSPENDED, flagged "resident removed").AdminMustF-07

8.2 Permissions

IDRequirementUser typePrioritySource
FR-06A resident can create a one-time permission with: guest name (required, 1–60 characters), guest phone (optional), at least one active gate, a start and end date-time (end after start, at most 7 days apart, end in the future), and a total opening limit (integer 1–20, default 2).ResidentMustF-01, F-03
FR-07A resident can create a recurring permission with: guest name, optional phone, at least one active gate, a date range (at most 365 days), one or more weekdays, one daily time window (start before end, same calendar day), and a total opening limit (integer 1–500, default 20). Times are evaluated in the community's time zone.ResidentMustF-02, F-03
FR-08The opening limit is cumulative over the permission's whole lifetime and never resets (not daily, not weekly, not on edit, not on suspend or resume). Each granted opening increases the used count by exactly 1. Denied attempts do not count.SystemMustF-03
FR-09When creating or editing a permission, a resident can select one or more active gates. The permission is valid only at the selected gates. Gate deactivation is handled by FR-04 (deny with GATE_INACTIVE). The permission keeps the deactivated gate in its gate list and shows it as unavailable, and the resident can remove it by editing the permission.ResidentShouldF-06
FR-10A resident can suspend an active permission and resume a suspended one. While suspended, every gate-open request is denied with reason SUSPENDED. Resuming does not extend the validity window or reset the counter.ResidentMustF-04
FR-11A resident can cancel a permission after a confirmation step. Cancellation is permanent: the permission cannot be resumed or edited, and its invitation link shows the "cancelled" state. Cancelling an already cancelled permission changes nothing.ResidentMustF-04
FR-12A resident can edit the validity window, schedule, gates and limit of a permission that is not cancelled. The new limit cannot be lower than the used count. Changes apply from the next gate-open request. The invitation link stays the same.ResidentShouldF-01, F-02
FR-13The system derives each permission's displayed status. Stored states are ACTIVE, SUSPENDED and CANCELLED. The derived states are SCHEDULED (before start), EXPIRED (after end) and EXHAUSTED (used = limit). Evaluation order is: cancelled → suspended → expired → exhausted → scheduled → active (Diagram 2).SystemMustF-01–F-04
FR-14A resident can see a list of their own permissions, showing guest name, type, status, gates, next valid window and remaining openings, filterable by status (Active/Scheduled, Suspended, Ended).ResidentMustF-15

Diagram 2 · Permission lifecycle (states and transitions)
stateDiagram-v2
  [*] --> SCHEDULED: created (start in future)
  [*] --> ACTIVE: created (start now or earlier)
  SCHEDULED --> ACTIVE: start time reached
  ACTIVE --> SUSPENDED: resident suspends (FR-10) / resident removed (FR-05)
  SCHEDULED --> SUSPENDED: resident suspends
  SUSPENDED --> ACTIVE: resident resumes (FR-10)
  ACTIVE --> EXHAUSTED: used = limit (FR-08)
  EXHAUSTED --> ACTIVE: limit raised by edit (FR-12)
  ACTIVE --> EXPIRED: end time passed
  EXPIRED --> ACTIVE: end extended by edit (FR-12)
  ACTIVE --> CANCELLED: resident cancels (FR-11)
  SCHEDULED --> CANCELLED
  SUSPENDED --> CANCELLED
  EXHAUSTED --> CANCELLED
  EXPIRED --> CANCELLED
  CANCELLED --> [*]
What it shows: the states a permission can be in. Only ACTIVE, SUSPENDED and CANCELLED are stored. SCHEDULED, EXPIRED and EXHAUSTED are derived from time and the counter (FR-13). Why it matters: only an ACTIVE permission, inside its current time window, can produce a grant. CANCELLED is terminal. Resuming never resets the counter (FR-08, FR-10).
