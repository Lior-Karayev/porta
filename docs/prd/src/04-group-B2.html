8Functional Requirements

The requirements are grouped by feature group. Each has an ID, a description, the relevant user type, a priority and its feature group. IDs from v1.0 are kept, so numbering has gaps. Retired IDs are listed in Section 7.6. Every requirement is enforced on the server where it concerns access (FR-03).

8.1 P-F01 · Authentication and user management

IDRequirementUser typePriorityGroup
FR-01A person can create an account with full name, email and a password of at least 8 characters, and sign in and out. An email address can belong to only one account. A signed-in session persists across app restarts until the user signs out or the session expires (NFR-08). Password reset by email is a Could.Resident, AdminMustP-F01
FR-02A newly registered user joins a community by entering its community code. The membership stays Pending until an administrator decides. Pending users only see a waiting screen and can sign out.ResidentMustP-F01
FR-03The system enforces the role table in Section 4 on every server-side operation, not only in the user interface. A disallowed operation is rejected and makes no change.AllMustP-F01
FR-04Gates are created by the project team's setup script, with a name (2–40 characters, unique in the community) and an active flag. Residents can choose only from the community's active gates. Every gate-open request for an inactive gate is denied with reason GATE_INACTIVE.SystemMustP-F01
FR-05An administrator sees the list of pending residents, with each one's name, email and request date, and can approve (after a confirmation step) or reject each one. The decision, who made it and when are stored with the membership (NFR-20). A rejected user sees an explanation and can enter a different code, including the same community's code again, which creates a new pending request, or sign out. A pending user can cancel their request. Removing a resident who has left is done by the project team with the setup script, at the administrator's request (D-31). It sets the membership to REMOVED. From then on, every request on that resident's permissions is denied with SUSPENDED (Diagram 3, check 4), the resident can no longer create permissions, and they see the "Membership removed" screen.AdminMustP-F01

8.2 P-F02 · Permission management

IDRequirementUser typePriorityGroup
FR-06A resident can create a one-time permission with:
  • a guest name (required, 1–60 characters)
  • exactly one active gate (pre-selected when the community has only one)
  • a start and end date-time: end after start, at most 7 days apart, end in the future
  • a total opening limit (an integer 1–20, default 2, enough for entry and exit)
Start and end are absolute points in time, entered and shown in the community time zone. A local time that doesn't exist because of a daylight-saving change is rejected with a message. A repeated (ambiguous) local time is interpreted as its first occurrence.		ResidentMustP-F02
FR-07A resident can create a recurring permission with:
  • a guest name and exactly one active gate
  • a date range of local calendar dates: first and last date both inclusive, at most 365 days
  • one or more weekdays
  • one daily time window: start before end, on the same calendar day, start-inclusive and end-exclusive
  • a total opening limit (an integer 1–500, default 20)
The server evaluates each request time in the community's time zone, including across daylight-saving changes.		ResidentMustP-F02
FR-08The opening limit is cumulative over the permission's whole lifetime and never resets (not daily, not weekly, not on suspend or resume). Each granted opening increases the used count by exactly 1. Denied attempts do not count.SystemMustP-F02
FR-10A resident can suspend an active or scheduled permission and resume a suspended one. While suspended, every gate-open request is denied with reason SUSPENDED. Resuming does not extend the validity window or reset the counter. The displayed status is derived again (FR-13), so it may come back as scheduled, active, expired or exhausted.ResidentMustP-F02
FR-11A resident can cancel a permission after a confirmation step. Cancellation is permanent: the permission cannot be resumed, and its invitation link shows the "cancelled" state. Cancelling an already cancelled permission changes nothing. To change a permission's details, the resident cancels it and creates a new one.ResidentMustP-F02
FR-13The system derives each permission's displayed status. Stored states are ACTIVE, SUSPENDED and CANCELLED. The derived states are SCHEDULED (before start), EXPIRED (after end) and EXHAUSTED (used = limit). Display precedence is: cancelled → suspended → expired → exhausted → scheduled → active (Diagram 2). When several conditions apply to a gate-open request, the guest sees the reason from the first failing check, in the order of Diagram 3.SystemMustP-F02
FR-14A resident can see a list of their own permissions, showing guest name, type, status, gate, next valid window and remaining openings, filterable by status: Active (active and scheduled), Suspended, and Ended (expired, exhausted, cancelled). When the resident has no permissions, an empty state explains how to create the first one. Opening an item shows its details (S-04).ResidentMustP-F02

8.3 P-F03 · Guest invitations and sharing

IDRequirementUser typePriorityGroup
FR-15Creating a permission generates exactly one unique, unguessable invitation link for it (token properties: NFR-05). The owning resident can view and re-share the link from any of their devices. Nobody else can read it, including administrators.SystemMustP-F03
FR-16A resident can share the invitation link through the device's native share options or copy it to the clipboard. The shared message contains the link and the guest-facing details (guest name, gate, validity summary, number of openings), with no resident address. Creating a permission is idempotent: a repeated save carrying the same client request ID returns the first result and creates nothing new.ResidentMustP-F03
FR-18A resident can show a QR code that encodes the same invitation link, on screen and full-screen for scanning.ResidentMustP-F03
FR-22On supported devices where the app is installed, opening an invitation link opens the matching in-app invitation screen (Android App Links / iOS Universal Links). In every other case the link opens the browser page, with identical behaviour. May be deferred (D-27).Registered guestCouldP-F03

8.4 P-F04 · Guest access and simulated gate

IDRequirementUser typePriorityGroup
FR-19Anyone opening a valid invitation link in a mobile browser, without registering, sees: the community name, the gate name, the validity summary, whether it is valid right now (and the next window if not), the remaining openings, and an "Open gate" action. The page does not show the resident's phone or address.GuestMustP-F04
FR-20A guest can request an opening of the gate on the page. The server validates the request using the rules in Diagram 3. A grant commits in one atomic transaction: the request receipt, the counter increase, the simulated gate's open-until time (FR-24) and the event record (FR-26). Notifications are sent only after the commit. The page then shows the result and the updated remaining openings.GuestMustP-F04
FR-21On denial, the guest page shows a short reason in plain language, with guidance ("Your access starts on Tue 08:00", "No openings left: contact your host"). Reason codes: INVALID_LINK, NOT_STARTED, OUTSIDE_HOURS, EXPIRED, EXHAUSTED, SUSPENDED, CANCELLED, GATE_INACTIVE, GATE_NOT_ALLOWED, RATE_LIMITED, DUPLICATE_REQUEST. An invalid link reveals nothing about any permission. RATE_LIMITED is shown as "Too many attempts. Please wait a minute and try again."GuestMustP-F04
FR-24Each gate has a simulated state, OPEN or CLOSED, derived from its stored open-until time: the gate is OPEN while the current time is before it. A grant sets open-until to the grant time plus 5 seconds, so a new grant while the gate is open restarts the 5 seconds.SystemMustP-F04
FR-25An administrator can open the Gate simulator screen (S-10). It shows each gate's live state and the last events (time, guest name, result), updated without a manual refresh.AdminMustP-F04

8.5 P-F05 · Activity history and notifications

IDRequirementUser typePriorityGroup
FR-26The system records every gate-open request, granted and denied, with: time, permission, gate, channel (web / app), result and reason code. To keep the history usable, consecutive RATE_LIMITED denials are recorded as one summary event per invitation (or per client IP for invalid links) per minute, including the number of attempts. Nobody can edit or delete these records through the app.SystemMustP-F05
FR-27A resident can see the activity history of their own permissions, newest first, filterable by permission and by result. It works whether or not notifications are enabled.ResidentMustP-F05
FR-29A resident receives a push notification when a guest is granted an opening on one of their permissions, where the device and platform allow it. Notifications can be turned on or off per permission (default on), on S-03 and later on S-04, and all at once in Settings (S-12). This is a preference only, so changing it is not editing the permission.ResidentShouldP-F05

8.6 P-F06 · AI-assisted permission creation

IDRequirementUser typePriorityGroup
FR-35A resident can describe a permission in free text, in Hebrew or English, up to 300 characters. The system returns a structured draft (type, dates, days, hours, gate, opening limit, guest name) and marks every field it could not determine as "please choose".ResidentMustP-F06
FR-41The draft opens in the regular creation form (S-03), with the AI-filled fields visibly marked. No permission is created until the resident reviews the draft and saves it. Fields the AI could not determine start empty, without the manual form's pre-selected gate or default limit. A value outside the FR-06/FR-07 limits, or a gate name that doesn't match exactly one active gate of the resident's community, is never pre-filled: the field is cleared and flagged with the reason. The server validates the saved permission exactly like a manually entered one.ResidentMustP-F06
FR-42The manual form opens with the resident's text kept and a short explanation in any of these cases:
  • the AI service is unavailable or takes longer than 8 seconds
  • it is not configured or approved
  • the free quota is used up
  • the provider's free offer has changed
  • the resident or the project has reached its daily limit (NFR-21)
The backend has a switch that turns AI requests off and answers with a controlled "unavailable" response. It never falls back to a paid model or another provider. Every other function works without the AI service.		ResidentMustP-F06
Diagram 2 · Permission lifecycle (states and transitions)
stateDiagram-v2
  [*] --> SCHEDULED: created (start in future)
  [*] --> ACTIVE: created (start now or earlier)
  SCHEDULED --> ACTIVE: start time reached
  ACTIVE --> SUSPENDED: resident suspends (FR-10)
  SCHEDULED --> SUSPENDED: resident suspends
  SUSPENDED --> ACTIVE: resume, inside validity (FR-10)
  SUSPENDED --> SCHEDULED: resume, before start
  SUSPENDED --> EXPIRED: resume, after end
  SUSPENDED --> EXHAUSTED: resume, used = limit
  ACTIVE --> EXHAUSTED: used = limit (FR-08)
  ACTIVE --> EXPIRED: end time passed
  ACTIVE --> CANCELLED: resident cancels (FR-11)
  SCHEDULED --> CANCELLED
  SUSPENDED --> CANCELLED
  EXHAUSTED --> CANCELLED
  EXPIRED --> CANCELLED
  CANCELLED --> [*]
What it shows: the states a permission can be in. Only ACTIVE, SUSPENDED and CANCELLED are stored. SCHEDULED, EXPIRED and EXHAUSTED are derived from time and the counter (FR-13). Why it matters: only an ACTIVE permission, inside its current time window, can produce a grant. EXPIRED and EXHAUSTED are final in practice, because permissions cannot be edited in v2.0 (Section 7.6). CANCELLED is terminal. Resuming re-derives the status, so it can lead to any of four states, and it never resets the counter (FR-08, FR-10).
