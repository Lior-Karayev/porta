8Functional Requirements

Each requirement has an ID, a description, the relevant user type, a priority and its source capability (F-xx). Requirements FR-36–FR-40 belong to post-MVP capabilities. They are listed so that every one of the 21 capabilities is traced, and they carry the priority Won't for this release.

FR-01A person can create an account with full name, email and a password of at least 8 characters, and sign in and out. Password reset by email is a Should. A signed-in session persists across app restarts until the user signs out or the session expires (NFR-08).Resident, AdminMustF-07
FR-02A newly registered user joins a community by entering its community code. The membership stays Pending until an administrator approves it. Pending users can only see a waiting screen.Resident, AdminMustF-07
FR-03The system enforces the role table in Section 4 on every server-side operation, not only in the user interface. A disallowed operation is rejected and makes no change.AllMustF-07

FR-05An administrator can approve or reject pending residents, and remove an approved resident. Removing a resident suspends all of that resident's permissions immediately (status SUSPENDED, flagged "resident removed").AdminMustF-07

8.2 Permissions

IDRequirementUser typePrioritySource
FR-06A resident can create a one-time permission with: guest name (required, 1–60 characters), at least one active gate (pre-selected when the community has only one), a start and end date-time (end after start, at most 7 days apart, end in the future), and a total opening limit (integer 1–20, default 2, enough for entry and exit). Start and end are absolute points in time, entered and shown in the community time zone. A local time that doesn't exist because of a daylight-saving change is rejected with a message. A repeated (ambiguous) local time is interpreted as its first occurrence.ResidentMustF-01, F-03
FR-07A resident can create a recurring permission with: guest name, at least one active gate, a date range of local calendar dates (first and last date both inclusive, at most 365 days), one or more weekdays, one daily time window (start before end, same calendar day, start-inclusive and end-exclusive), and a total opening limit (integer 1–500, default 20). The server evaluates each request time in the community's time zone, including across daylight-saving changes.ResidentMustF-02, F-03
FR-08The opening limit is cumulative over the permission's whole lifetime and never resets (not daily, not weekly, not on edit, not on suspend or resume). Each granted opening increases the used count by exactly 1. Denied attempts do not count.SystemMustF-03
FR-09When creating or editing a permission, a resident can select one or more active gates. The permission is valid only at the selected gates. Gate deactivation is handled by FR-04 (deny with GATE_INACTIVE). The permission keeps the deactivated gate in its gate list and shows it as unavailable, and the resident can remove it by editing the permission.ResidentShouldF-06
FR-10A resident can suspend an active or scheduled permission and resume a suspended one. While suspended, every gate-open request is denied with reason SUSPENDED. Resuming does not extend the validity window or reset the counter, and the displayed status is derived again (FR-13), so it may come back as scheduled, active, expired or exhausted. A permission suspended because its resident was removed (FR-05) cannot be resumed.ResidentMustF-04
FR-11A resident can cancel a permission after a confirmation step. Cancellation is permanent: the permission cannot be resumed or edited, and its invitation link shows the "cancelled" state. Cancelling an already cancelled permission changes nothing.ResidentMustF-04
FR-12A resident can edit the validity window, schedule, gates and limit of a permission that is not cancelled. The new limit cannot be lower than the used count. Changes apply from the next gate-open request. The invitation link stays the same.ResidentShouldF-01, F-02
FR-13The system derives each permission's displayed status. Stored states are ACTIVE, SUSPENDED and CANCELLED. The derived states are SCHEDULED (before start), EXPIRED (after end) and EXHAUSTED (used = limit). Display precedence is: cancelled → suspended → expired → exhausted → scheduled → active (Diagram 2). When several conditions apply to a gate-open request, the guest sees the reason from the first failing check, in the order of Diagram 3.SystemMustF-01–F-04
FR-14A resident can see a list of their own permissions, showing guest name, type, status, gates, next valid window and remaining openings, filterable by status: Active (active and scheduled), Suspended, and Ended (expired, exhausted, cancelled). When the resident has no permissions, an empty state explains how to create the first one.ResidentMustF-01, F-02

8.3 Invitations and guest access

IDRequirementUser typePrioritySource
FR-15Creating a permission generates exactly one active, unique, unguessable invitation link for it (token properties: NFR-05). The owning resident can view and re-share the current link from any of their devices. Nobody else can read it, including administrators.SystemMustF-08
FR-16A resident can share the invitation link through the device's share options or copy it to the clipboard. The shared message contains the link and the guest-facing validity summary, with no resident address. Creating a permission is idempotent: a repeated save carrying the same client request ID returns the first result and creates nothing new.ResidentMustF-08
FR-17A resident can regenerate a permission's link. The previous link stops working immediately and is treated as an invalid link (INVALID_LINK). The counter and settings are kept.ResidentShouldF-08
FR-18A resident can show a QR code that encodes the same invitation link, on screen and inside the share message.ResidentShouldF-10
FR-19Anyone opening a valid invitation link in a mobile browser, without registering, sees: the community name, the gate name(s), the validity summary, whether it is valid right now (and the next window if not), remaining openings, and an "Open gate" action for each gate. The page does not show the resident's phone or address.GuestMustF-09
FR-20A guest can request an opening of one gate on the page. The server validates the request using the rules in Diagram 3. A grant commits in one atomic transaction: the request receipt, the counter increase, the simulated gate's open-until time (FR-24) and the event record (FR-26). Notifications are sent only after the commit. The page then shows the result and the updated remaining openings.GuestMustF-09, F-03
FR-21On denial, the guest page shows a short reason in plain language with guidance ("Your access starts on Tue 08:00", "No openings left: contact your host"). Reason codes: INVALID_LINK, NOT_STARTED, OUTSIDE_HOURS, EXPIRED, EXHAUSTED, SUSPENDED, CANCELLED, GATE_INACTIVE, GATE_NOT_ALLOWED, RATE_LIMITED. An invalid link reveals nothing about any permission.GuestMustF-09
FR-22On supported devices where the app is installed, opening an invitation link opens the matching in-app invitation screen (Android App Links / iOS Universal Links). In every other case the link opens the browser page with identical behaviour.Registered guestShouldF-09
FR-23A signed-in user can save a received invitation to "My invitations" in the app and open it from there later.Registered guestCouldF-09

8.4 Simulated gates, logs and notifications

IDRequirementUser typePrioritySource
FR-24Each gate has a simulated state, OPEN or CLOSED, derived from its stored open-until time: the gate is OPEN while the current time is before it. A grant sets open-until to the grant time plus 5 seconds, so a new grant while the gate is open restarts the 5 seconds.SystemMustSimulation
FR-25An administrator can open the Gate simulator screen (S-10). It shows each gate's live state and the last event (time, guest name, result), updated without a manual refresh.AdminMustSimulation
FR-26The system records every gate-open request, granted and denied, with: time, permission, gate, channel (web / app), result and reason code. Residents and administrators cannot edit or delete these records.SystemMustF-13
FR-27A resident can see the activity log of their own permissions, newest first, filterable by permission and by result.ResidentMustF-13
FR-28An administrator can see the community-wide activity log, filterable by gate, date range and result.AdminShouldF-13
FR-29A resident receives a push notification when a guest is granted an opening on one of their permissions. Notifications can be turned on or off per permission (default on).ResidentShouldF-14
FR-30A resident receives a reminder when a permission has 1 opening left or expires within 24 hours.ResidentCouldF-14
FR-31The resident home screen shows a summary: number of active permissions, entries today, and permissions ending within 7 days. Each item opens the matching filtered list.ResidentShouldF-15

8.5 Creation helpers and AI

IDRequirementUser typePrioritySource
FR-32A resident can create a permission through a guided wizard that asks one question per step (who → one-time or recurring → when → which gates → how many openings → review). The result is identical to the form (FR-06/FR-07) and passes the same validation.ResidentShouldF-21
FR-33A resident can save a permission's settings, without its dates, as a named template and start a new permission from it.ResidentCouldF-05

The system proposes a filled-in draft (type, dates, days, hours, gates, limit) and highlights any field it could not determine. Diagram 2 · Permission lifecycle (states and transitions)
stateDiagram-v2
  [*] --> SCHEDULED: created (start in future)
  [*] --> ACTIVE: created (start now or earlier)
  SCHEDULED --> ACTIVE: start time reached
  ACTIVE --> SUSPENDED: resident suspends (FR-10) / resident removed (FR-05)
  SCHEDULED --> SUSPENDED: resident suspends
  SUSPENDED --> ACTIVE: resident resumes (FR-10)
  ACTIVE --> EXHAUSTED: used = limit (FR-08)
  EXHAUSTED --> ACTIVE: limit raised by edit (FR-12)
  ACTIVE --> EXPIRED: end time passed
  EXPIRED --> ACTIVE: end extended by edit (FR-12)
  ACTIVE --> CANCELLED: resident cancels (FR-11)
  SCHEDULED --> CANCELLED
  SUSPENDED --> CANCELLED
  EXHAUSTED --> CANCELLED
  EXPIRED --> CANCELLED
  CANCELLED --> [*]
What it shows: the states a permission can be in. Only ACTIVE, SUSPENDED and CANCELLED are stored. SCHEDULED, EXPIRED and EXHAUSTED are derived from time and the counter (FR-13). Why it matters: only an ACTIVE permission, inside its current time window, can produce a grant. CANCELLED is terminal. Resuming never resets the counter (FR-08, FR-10).
