What it shows: entities E-01 to E-12 and how they relate. Only key attributes are shown; the full fields are in the table above.
  • A permission belongs to one resident.
  • A permission is valid at one or more gates through PermissionGate.
  • A permission has an optional recurrence rule.
  • A permission keeps a history of invitations. Regenerating a link revokes the old one (FR-17).
  • Every request becomes an AccessEvent.
Why it matters: separating Invitation from Permission makes link regeneration possible without losing the counter. Making AccessEvent append-only gives a trustworthy audit trail.

11.4 The AI component (FR-35, Could)

InputThe resident's free text (≤ 300 characters), today's date, the community time zone, and the names of the community's active gates. No personal data beyond the guest name the resident typed. No phone numbers, no history.
OutputA structured draft: type, validFrom, validUntil, daysOfWeek, startTime, endTime, gateNames, maxOpenings, guestName, plus a list of fields it could not determine. The output is checked against a strict schema.
When it is wrongThe draft is always shown in the normal form for review, and nothing is saved without the resident's confirmation. Values outside FR-06/FR-07 limits, or gate names that don't match a real gate, are cleared and flagged. The server re-validates every field exactly as for manual input.
When it is unavailableTimeout after 8 s, or any error: the manual form opens with the text preserved (AC-13.2). Core functionality never depends on the AI.
Cost and approvalRequires a paid API key. It needs explicit team approval of cost before any use (Budget Policy, Q-04).
